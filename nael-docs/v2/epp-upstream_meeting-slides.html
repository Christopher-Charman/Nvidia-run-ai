Where we are today

One profile, fixed weights, and background weight tuning in progress

Today · ✅ exists

The EPP runs one profile with fixed scorer weights

        │  run "balanced"
        ▼
✅ Profile "balanced"    queue ×2 · KV ×2 · prefix ×3 → max-score picker   (default-plugins.yaml, llm-d Router main)
        │

Selected pod             score(p) = Σ w[j] × s[j,p]
  • Scores react to live metrics every request. Weights never change.
  • Under a hotspot, the prefix scorer keeps pulling traffic to the hot pod with the same weight as when the pool was idle.
  • Other handlers exist on main: headerprofile (caller chooses), disagg (prefill/decode), dataparallel. The loader allows one handler.
  • The EPP code now lives in llm-d/llm-d-router; GAIE keeps only the InferencePool API.

Today · adaptive routing, in progress

Background detectors retune the weights

✅ Endpoint metrics store  ──►  🆕 Imbalance detector   CVn of KV usage and assigned requests, pool-wide
                           ──►  🆕 Pressure detector    Σ waiting / Σ (waiting + running)
                                        │  smoothed 0.1 × prev + 0.9 × new
                                        ▼
                                 🆕 Adaptive configurator  sigmoid(imbalance) → distribution budget D, affinity A = 1 − D
                                        │  rewrites scorer weights inside every profile, each cycle
                                        ▼
                                 ✅ Scheduler              requests use the current weights; zero per-request work
  • Merged prerequisites: #2119 scorer categories (affinity / distribution), #2207 float weights.
  • Experimental branch adaptive-with-pressure; hotspot benchmark reported on 8 × A100.
  • Output is a continuous, derived weight vector. #1992 also lists an alternative: select among groups of scorers instead of adjusting each weight.

A proposal

The "select among groups" alternative, built on the same signals

Proposal · the idea

Operators write a few profiles; a rule picks one per request

✅ Locate and screen candidates
        │  per-pod snapshots: WaitingQueueSize · RunningRequestsSize · UpdateTime
        ▼
🆕 Produce    one pass over candidates → two signals, stored on the request
        │
        ▼
✅ Admission
        │
        ▼
🆕 Pick       ordered rules → one of the configured profiles         ◄──► 🆕 remembers last choice
        │
        ▼
✅ Run selected profile   cache-oriented / balanced / load-oriented, fixed weights, unchanged
The request chooses a fixed, operator-written policy; that policy chooses the pod. The log says which rule fired and why.

Proposal · one request, step by step (1 of 2)

Before the decision

  1. ✅ The client sends a request: "model X, here is my prompt".
  2. ✅ The Gateway catches it, holds it, and asks the EPP: "which pod should this go to?"
  3. ✅ The EPP reads the body and notes the model and the prompt.
  4. ✅ The EPP lists the pods that can serve this model and are ready. For each it takes the latest numbers already in memory: waiting, running, KV usage, and when they were refreshed.
  5. ✅ The prefix lookup checks which of those pods has already seen the start of this prompt.
  6. 🆕 Our plugin walks the same pods once and writes two numbers on the request: how uneven the queues are (cv) and how much is waiting overall (P).If any pod's numbers are stale, it marks the summary invalid instead.
  7. ✅ Admission asks: is there room right now? If not, the request waits in line.

Proposal · one request, step by step (2 of 2)

The decision, and after

  1. 🆕 Our plugin asks: "which profile did I choose last time, and is the signal still inside that profile's stay band?"→ yes: keep the same profile. → no: first matching rule (very uneven → load-oriented, almost nothing waiting → cache-oriented), else the default. It remembers the choice. Today this step does not exist: the one fixed profile always runs.
  2. ✅ The chosen profile runs exactly as today: filters drop unfit pods, scorers rate the rest with that profile's fixed weights, the picker takes the best → pod-1.
  3. 🆕 Our plugin writes one log line: which rule fired, at what signal value, which profile, which pod.
  4. ✅ The EPP answers the Gateway with one header: "send it to pod-1". Nothing else it computed leaves the EPP.
  5. ✅ The Gateway forwards the original, untouched request to pod-1.
  6. ✅ vLLM on pod-1 runs prefill (fast if the prefix is cached) and decode, and streams the answer back through the Gateway to the client.
  7. ✅ The EPP notes "pod-1 has now seen this prefix" for next time.

Two new steps (6 and 8) and one new log line (10). Everything else is today's EPP.

Proposal · the signals

Two numbers in 0..1, from metrics the EPP already has

SignalFormula over the candidatesAnswersSource, per pod ✅
imbalance (cv)min(1, σ / mean) of the queues; 0 when mean < gateHow uneven?WaitingQueueSize
pressure (P)Σ waiting / Σ (waiting + running)How much is waiting?WaitingQueueSize, RunningRequestsSize

Key point · why not the mean queue

queues 10, 10, 10   mean 10   cv 0.00   even
queues  0,  0, 30   mean 10   cv 1.00   hotspot
queues 18, 20, 22   mean 20   cv 0.10   busy, even
queues  5, 20, 35   mean 20   cv 0.75   busy, uneven

The mean gives the same answer to each pair. Unevenness is the one thing we switch for, and the one thing a mean cannot see.

Same statistics as the detectors

  • P is the pressure detector's formula, unchanged
  • cv is the imbalance detector's CV, scoped to the request's candidates
  • Read via GetMetrics(), like queue-scorer. No new scraping.

Proposal · the rules

Each rule has an enter and an exit threshold

Rules, first match wins

hotspot   imbalance ≥ 0.5   → load-oriented
          leave only below 0.35
idle      pressure  < 0.2   → cache-oriented
          leave only above 0.3
default                      → balanced

The plugin remembers one thing: the current profile. Between exit and enter it keeps it.

Key point · why two thresholds, not one

signal   one threshold 0.5    enter 0.5 / exit 0.35
0.48     balanced             balanced
0.52     load      flip       load      enter
0.47     balanced  flip       load      held
0.55     load      flip       load      held
0.40     balanced  flip       load      held
0.30     balanced             balanced  exit

Scrape jitter around a single threshold flips the profile on consecutive requests and wastes the shared prefix cache. A thermostat: on at 25, off at 23.

Proposal · configuration

What the operator writes

- type: adaptive-profile-handler
  parameters:
    defaultProfile: balanced
    maxMetricAge: 1s
    minMeanQueue: 3        # gate for cv
    smoothing: 0.1         # α, 0 disables
    rules:
    - name: hotspot
      when: { signal: imbalance, operator: gte,
              enter: 0.5, exit: 0.35 }
      profile: load-oriented
    - name: idle
      when: { signal: pressure, operator: lt,
              enter: 0.2, exit: 0.3 }
      profile: cache-oriented

Key point · thresholds are ratios, not counts

Pool20 waiting is…P
8B · 1 × A100 (~256 slots)~8%, idle0.07
70B · 8 × A100 (~32 slots)~60%, busy0.38

"20 waiting requests" means nothing without capacity. P and cv carry the capacity inside the ratio, so one YAML works on every model and GPU. The only count left is the gate "is there anything worth redistributing".

Profiles unchanged: cache 4/1/1 · balanced 2/1/1 · load 1/1/4. No new CRD. Startup validation: exit < enter for gte, exit > enter for lt.

Proposal · step by step

What happens on one request

  1. Locate and screen the candidate pods. (unchanged)
  2. Walk the candidates once; read waiting, running and update time for each.
  3. If any metric is missing or older than the limit, mark the summary invalid.
  4. Compute the mean, the spread (cv, 0 if the mean is below the gate) and the waiting share (P). Save them on the request with an expiry time.
  5. Continue through admission. (unchanged)
  6. At Pick: if there is a current profile and the signal is still inside its stay band, keep it.
  7. Otherwise take the first rule whose enter threshold holds, or the default. Remember it.
  8. Run that profile's filters, scorers and picker; return its result. (unchanged)

Proposal · boundaries

Scope of a first version

In

  • One plugin: DataProducer + ProfileHandler
  • Two signals, ordered rules with enter/exit, default profile
  • Candidate-scoped evaluation, one pass, in-memory only
  • Per-request log line and selection counter

Not yet

  • Coexistence with disagg-profile-handler (one handler seat)
  • Partial metric coverage instead of all-or-nothing
  • Deriving profile weights from a budget
  • Retry with another profile on failure

Decisions

What I need from you before this goes to the community

Decisions

Four questions for this meeting

  1. Where should selection live? A separate ProfileHandler (request-scoped, but takes the only handler seat), or a mode: discrete inside the configurator (pool-scoped, coexists with disagg)?
  2. Normalization of cv. Plain σ / mean capped at 1, or the detectors’ (σ / mean) / √(N−1)? Copying it makes a later change of signal source a no-op.
  3. Benchmark shape. Default profile vs adaptive handler on 4 GPUs with a real model and a shared-prefix hotspot. Is that the comparison that would convince the llm-d Router maintainers?
  4. Which branch and settings produced the reported configurator results, so they can be cited correctly as prior art?
