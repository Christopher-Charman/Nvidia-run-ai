Select the profile on imbalance,
not on the mean

Rule-based scheduling-profile selection for the EPP, revised.
For discussion with Nir before opening an upstream issue.

Draft proposal   Not implemented   Numbers illustrative

The story in 3 lines

Where we are, what broke, what I propose

  1. Today: the EPP runs one profile with fixed scorer weights. Two ideas exist for adapting: Nir's background weight tuning, and my per-request profile selection on mean queue depth.
  2. What broke in mine: the mean cannot see a hotspot, the choice flips between requests, and the thresholds are raw request counts that mean nothing across models.
  3. Proposal: select on two normalized signals, imbalance and pressure, with enter/exit bounds. Same statistics Nir already uses, so this becomes the discrete, explainable mode of his work, not a competitor.

Scores react to live metrics. Weights do not. Under a hotspot the prefix scorer keeps pulling traffic to the hot pod.

Current state · two approaches

Two ways to adapt, already on the table

Nir · background weight tuning

  • Detectors measure imbalance (CV of KV + assigned) and pressure (waiting share), pool-wide
  • Configurator rewrites scorer weights continuously via a sigmoid
  • Zero work on the request path
  • Prerequisites merged: #2119 categories, #2207 float weights

Nael v1 · per-request profile selection

  • One plugin reads the request's candidates, computes mean queue
  • Ordered rules pick one of predefined profiles with fixed weights
  • Explainable: "rule X matched → profile Y"
  • Draft only, no prototype, no numbers

Continuous versus discrete. Pool-scoped versus request-scoped. Both want the same outcome: affinity when even, distribution when uneven.

Three things that break in v1

Wrong measurement · no memory · wrong units

Problem 1 · wrong measurement

The mean cannot see a hotspot

Candidate queuesMeanv1 selectsWhat is really happening
10, 10, 1010balanced ✔Even load, affinity is safe
0, 0, 3010balanced ✘One hot pod, two idle. Should distribute
18, 20, 2220load-oriented ✘Busy but even. Queue scorer cannot help
5, 20, 3520load-oriented ✔Busy and uneven

Rows 1 and 2 get the same answer. Rows 3 and 4 get the same answer. The one thing we switch profiles for, unevenness, is the one thing the mean cannot measure.

Problem 3 · no memory

Every request decides from scratch, so the choice flips

request 1   signal 0.48   0.48 ≥ 0.5 ?  no   → balanced
request 2   signal 0.52   0.52 ≥ 0.5 ?  yes  → load-oriented     flip
request 3   signal 0.47   0.47 ≥ 0.5 ?  no   → balanced          flip
request 4   signal 0.55   0.55 ≥ 0.5 ?  yes  → load-oriented     flip
request 5   signal 0.40   0.40 ≥ 0.5 ?  no   → balanced          flip
  • Nothing changed in the pool. This is scrape jitter around the threshold.
  • Same-session requests land on different pods. The KV cache they share is wasted.
  • We pay for adaptation and lose affinity at the same time.

Problem 6 · wrong units

"20 waiting requests" means nothing without capacity

PoolCan run at once20 waiting is…v1 rule mean ≥ 20
Llama 8B · 1 × A100~256~8% of capacity, idleload-oriented ✘ far too early
Llama 70B · 8 × A100~32~60% of capacity, busyload-oriented ✔
  • One YAML, one number, right on one pool and wrong on the other.
  • Every operator must retune per model and per GPU, and nothing tells them how.

#ProblemBecause the rule input is…

The proposal

Two normalized signals · enter/exit bounds · same plugin

Proposal · signals

Two numbers between 0 and 1, from metrics the EPP already has

SignalFormulaAnswersSource (per pod, ✅ exists)
cv imbalancemin(1, σ / mean) of the queues, 0 if mean < gateHow uneven is the load?WaitingQueueSize
P pressureΣ waiting / Σ (waiting + running)How much is waiting?WaitingQueueSize, RunningRequestsSize
  • Both are the exact statistics of Nir's imbalance and pressure detectors, scoped to the request's candidates instead of the pool.
  • No new scraping. Read via GetMetrics() like queue-scorer does. The pool averages exported to Prometheus are not usable: pool-wide, truncated, and not reachable from a plugin.

Rules: cv ≥ 0.5 → load-oriented, then P < 0.2 → cache-oriented, else balanced. The two wrong answers of v1 are now right; nothing that was right became wrong.

Fix 3 · memory

Enter at 0.5, leave at 0.35, do nothing in between

Before · one threshold

0.48  balanced
0.52  load         flip
0.47  balanced     flip
0.55  load         flip
0.40  balanced     flip
0.30  balanced

4 flips

After · enter 0.5 / exit 0.35

0.48  balanced     no regime, below enter
0.52  load         enter
0.47  load         held, above exit
0.55  load         held
0.40  load         held, above exit
0.30  balanced     exit

1 entry, 1 exit

The plugin remembers one thing: the current profile. A thermostat: on at 25, off at 23, no flicker at 24. Smoothing (Nir's 0.1/0.9) is optional on top; it trims spikes but does not prevent flips.

Fix 6 · units

Ask "what share is waiting", not "how many"

PoolwaitingrunningP = waiting / (waiting + running)Rule P ≥ 0.4 busy?
Llama 8B · 1 × A100202560.07no, idle ✔
Llama 70B · 8 × A10020320.38almost, busy ✔
  • The pod's capacity is built into the ratio. One threshold works on every model and GPU.
  • cv is already unitless. The only count left is the gate "mean < 3 → cv = 0", which just asks "is there anything worth redistributing".

Proposal · configuration

What the operator writes

v1

rules:
- name: high-queue
  when: { metric: waitingQueueSize,
          aggregation: mean,
          operator: gte, value: 20 }
  profile: load-oriented
- name: low-queue
  when: { metric: waitingQueueSize,
          aggregation: mean,
          operator: lt, value: 5 }
  profile: cache-oriented

v2

minMeanQueue: 3      # gate for cv
smoothing: 0.1       # α, 0 disables
rules:
- name: hotspot
  when: { signal: imbalance,
          operator: gte,
          enter: 0.5, exit: 0.35 }
  profile: load-oriented
- name: idle
  when: { signal: pressure,
          operator: lt,
          enter: 0.2, exit: 0.3 }
  profile: cache-oriented

Profiles and weights unchanged (cache 4/1/1, balanced 2/1/1, load 1/1/4). Only handler parameters change. Startup validation: exit < enter for gte, exit > enter for lt.

Proposal · boundaries

What stays, what is deliberately not here

Unchanged from v1

  • One plugin: DataProducer + ProfileHandler, no new CRD
  • Candidate-scoped evaluation
  • Predefined profiles, fixed weights
  • Default profile on invalid data, no retry

Tracked separately

  • Single ProfileHandler seat vs disagg-profile-handler
  • Producer budget, fallback metric, p99 benchmark
  • Partial metric coverage (≥ 80%) instead of full
  • Deriving profile weights from a budget

What I need from you

Four decisions, then a path to upstream

Decisions

Four questions for this meeting

  1. Where should selection live? A separate ProfileHandler (request-scoped, but takes the only handler seat), or a mode: discrete inside your configurator (pool-scoped, coexists with disagg)?
  2. Normalization of cv. Plain σ / mean capped at 1, or your (σ / mean) / √(N−1)? Copying yours makes a later switch of signal source a no-op.
  3. Does discrete selection sound worth benchmarking against your continuous weights on the same hotspot setup (8 pods, Llama 8B, GuideLLM)?
  4. Which branch and settings produced your reported results, especially whether the pressure cap was active?
